# Smart Clock desktop installer

For user instructions, see [Install and update with the desktop app](../docs/wiki/Desktop-App.md).

Build Windows from an isolated environment to avoid including unrelated packages:

```powershell
python -m venv outputs/desktop-build-env
outputs/desktop-build-env/Scripts/python.exe -m pip install "esphome==2026.10.1"
outputs/desktop-build-env/Scripts/python.exe -m pip check
outputs/desktop-build-env/Scripts/python.exe desktop/build_windows.py
outputs/desktop-build-env/Scripts/python.exe desktop/verify_windows.py --compile
$env:DESKTOP_PLATFORM = 'Windows-x64'
outputs/desktop-build-env/Scripts/python.exe desktop/package.py
outputs/desktop-build-env/Scripts/python.exe tests/web_installer_download_test.py
outputs/desktop-build-env/Scripts/python.exe desktop/verify_web_installer.py --compile
```

The Windows build machine needs Python; it automatically downloads a checksum-pinned
[MinGit distribution](https://gitforwindows.org/mingit.html), designed for bundling
in applications. A full Git/Bash installation is not included in the Windows app.
Distribute **only** `outputs/desktop-release/SmartClock-Windows-x64.exe`.
`outputs/SmartClock-Windows` is an internal build stage, not the delivered app.
The small setup EXE (about 23 KB) downloads its matching runtime asset (about 81 MB)
from an immutable official HTTPS release URL. Its expected size and full SHA-256
are compiled into the EXE. Python, Tk, ESPHome, the uploader and MinGit are in the
runtime; no package manager or archive utility is required on the user's computer.
Git uses solid LZMA2 compression; generated bytecode and optional Python IDE/demo
data are omitted. The runtime is activated under
`%LOCALAPPDATA%/SmartClock/application/<payload-id>` only after verification,
extraction and a core-library loading check. Subsequent launches reuse it offline.
No companion folder, manual extraction,
Python/Java installation or external archive utility is required. Firmware
toolchains are downloaded on first build. This preview is unsigned and has no
system-wide installer. Replacing the EXE preserves personal settings.

The downloader has bounded automatic retries, per-request/connect/read timeouts,
size limits, SHA-256 checks, safe Range resume, automatic restart when Range is
unsupported, cancellation and preserved partial files. Production accepts only
HTTPS, including redirects; test builds additionally allow loopback HTTP. It uses
the Windows proxy configuration and never disables certificate verification.
Corrupt/HTML/invalid-range content is discarded. Failed setup never activates a
partial runtime or deletes existing versions/settings. Downloaded verified ZIPs
are retained under the application cache's `downloads` directory for repair.

`build_web_installer.py` compiles the small installer from a generated runtime ZIP.
`DESKTOP_RELEASE_TAG` binds it to the release tag. The release must include the
exact content-addressed runtime ZIP; the installer does not fetch mutable `latest`
metadata. Local previews use a separate `TEST_DOWNLOAD` executable and localhost
server. They are outside `outputs/desktop-release` and are never uploaded as
release assets. The public URL cannot work before the release assets are published.

The form saves Wi-Fi, fallback hotspot and HA API settings under the current
user's application data directory. These files contain credentials in plain
text, as required by ESPHome. They are never included in the distribution.
Existing clocks should reuse their existing encryption key. Runtime settings
(brightness, alarms, etc.) remain in Home Assistant.

Check for updates checks GitHub's published releases, including betas, downloads
newer firmware source and selects it. Build & install compiles with the user's
settings before USB/OTA upload. It never installs public placeholder binaries.
This preview does not update the desktop application itself or read credentials
back from a device. The displayed version is the selected firmware source,
not an assertion about the version currently running on a connected clock.

USB bridges from Silicon Labs (CP210x), WCH (CH340/CH341), FTDI and Espressif
are prioritized and rescanned automatically. A bridge is a candidate, not proof
that the attached board is the correct ESP32; the uploader checks the chip.
Windows driver setup uses built-in Windows Update, filters updates by connected
USB hardware IDs, and requests elevation only for installation. Driver binaries
are not bundled, and availability depends on Windows Update. A vendor-only
driver may still require additional support. No driver is installed during builds.

Target for this preview: Windows 10/11 x64. Java is unused. .NET Framework for
the launcher and PowerShell/Windows Update for driver setup are Windows components.
`verify_windows.py` tests the bundled runtime with developer tools removed from
PATH. Local verification has completed a full firmware build. A clean Windows VM
and physical USB/OTA installation are still required before declaring the package
release-ready. CI repeats dependency checks and full compilation on native hosts.
Use `python desktop/verify_windows.py --compile` to additionally compile firmware
with the bundled runtime and a sanitized PATH. This can download several GB.

macOS: `python desktop/build_macos_dmg.py` creates **one universal
`outputs/desktop-release/SmartClock-macOS.dmg`** for Apple Silicon and Intel.
Open the image and double-click Smart Clock Setup. No ZIP extraction is required.
The launcher detects the physical hardware and selects the correct runtime even
when Terminal runs under Rosetta. The first launch opens an
automated Terminal setup window; no commands need typing. The installer downloads
checksum-pinned official Micromamba, then provisions private conda-forge
Python/Tk/Git/FreeType and the pinned ESPHome packages. It needs no Homebrew, Xcode,
existing Python or administrator installation. Package managers validate their
downloads; pip uses retries and fresh downloads, and optional native builds are
prevented from invoking Xcode. The runtime is marked complete only after package
and library checks pass. Later launches use it offline and open the GUI directly.

On a Mac, packaging uses native `hdiutil` to create and verify a compressed,
read-only HFS+ DMG. On Windows, it uses a build-only, checksum-pinned portable Go
SDK and [JetBrains' cross-platform DMG writer](https://github.com/JetBrains/go-dmg-writer)
to create an actual UDIF/HFSX disk image. The Windows adapter explicitly records
Mac 0755/0644 file modes and corrects the pinned writer's encoded-data-fork CRC.
Go and the writer are not distributed to users and are not runtime dependencies.
`build_macos_online.py` is an internal per-architecture app builder; its ZIPs stay
under `outputs/macos-dmg-build/internal-zips` when creating the DMG.

Run `python desktop/verify_macos_online.py` on a native Mac to verify the DMG
checksum, mount it read-only, validate executable modes, and run installation,
GUI/configuration and full compilation. The release workflow builds the DMG once,
then downloads and verifies that identical artifact on both native architectures.
Local Windows checks (`desktop/verify_dmg.py`) independently validate UDIF data and
master CRCs, extract the HFS filesystem with 7-Zip, check every file hash against
the build manifest, and inspect the stored Unix permissions. Shell syntax,
bootstrap binary hashes/architectures and prebuilt dependency availability were
also checked. A supplied Mac installation log confirms firmware compilation and
USB upload with written-data hash verification and reset. Native mounting of the
latest universal DMG and its automatic setup path still need confirmation.
`build_macos.py` is retained as an optional older offline packaging route and is
not used by the online-installer release jobs. Signing/notarization is not configured.

The existing `.github/workflows/release.yml` builds and tests all three packages
before attaching the Windows setup EXE/runtime ZIP, universal macOS DMG and SHA-256 files.
CI runs the distributed EXE from an otherwise empty folder, checks dependencies,
validates configuration, compiles firmware and verifies offline cache reuse. Its
native HTTP fault tests cover truncation, corruption, HTML, incorrect ranges,
ignored ranges, cancellation/resume, proxy blocks, throttling and file-access
failures. Native macOS jobs and
actual USB/OTA flashing have not been exercised in this local Windows session.

Implementation follows the [ESPHome CLI](https://esphome.io/guides/cli/).

Release integrity: `verify_package_sources.py` compares the packaged GUI, YAML,
headers, components and media byte for byte with the release checkout and rejects
missing/extra firmware or secrets. Windows also checks the runtime SHA and target
release URL; both native Mac jobs check client.zip from the mounted DMG.
`release-provenance.json` records the source commit, version and all asset hashes.
